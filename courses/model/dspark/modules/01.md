## [m1-bottleneck] LLM 推理的主要瓶颈

::: concept
title: 自回归生成的串行约束
why: 每个新 token 都依赖之前所有 token，这是推理 latency 的根本来源。

大型语言模型在 decode 阶段采用自回归方式：生成第 $t$ 个 token 时，必须先把前 $t-1$ 个 token 的 key/value 都计算好并保留在 KV cache 中。这带来两个直接后果：

- **计算并行度低**：虽然每次 forward 的矩阵乘法很大，但用户实际只拿到 1 个新 token。
- **内存墙**：随着序列变长，KV cache 容量和带宽成为瓶颈，尤其在大 batch 高并发场景。

这就是生产环境里 LLM 推理成本高、响应慢的核心原因。
:::

::: concept
title: 投机解码的基本思想
why: 用便宜的小模型先“猜”一串 token，再由大模型一次性验证，可以把串行变成批量。

投机解码（Speculative Decoding）的核心流程是：

1. **Draft**：用一个轻量 draft 模型一次性生成 $\gamma$ 个候选 token。
2. **Verify**：用目标大模型对这 $\gamma$ 个 token 做一次 forward，按规则接受或拒绝。
3. **Resample**：从第一个被拒绝的位置重新采样，并把已接受部分作为下一轮输入。

只要 draft 模型足够快、接受率足够高，就能把多次串行的大模型调用压缩成一次，整体吞吐显著提升。更重要的是，验证规则保证了输出分布与目标模型一致，因此**理论上无损**。

如果你希望快速了解 DSpark 的源头论文和关键基线，可以先跳到 [m2](m2.html) 的半自回归架构和 [m3](m3.html) 的置信度调度；想要查原始论文与实现细节，见 [m4](m4.html) 训练部署与 [m5](m5.html) 的对比表。

延伸阅读：
- [Accelerating Large Language Model Decoding with Speculative Sampling](https://arxiv.org/abs/2302.01318) —— 投机采样的早期工作，介绍了 draft + verify 的概率框架。详细讲解见 [m0 投机解码简史](m0.html)。
- [Fast Inference from Transformers via Speculative Decoding](https://arxiv.org/abs/2211.17192) —— 提出了保持目标分布无损的拒绝采样规则。详细讲解见 [m0 投机解码简史](m0.html)。

## [m1-drafter-tradeoffs] 自回归 draft 与并行 draft 各自卡在哪里

::: concept
title: 自回归 draft：强建模，但 draft 本身串行
why: 顺序生成能建模 token 间依赖，但 draft 成本随候选长度线性增长。

自回归 drafter（如 Eagle3）依次生成候选 token，每个位置都显式条件于前面已采样的 token。优点是序列内一致性强，在代码、数学等结构化任务上接受率较高。缺点是 draft 成本与块长 $\gamma$ 成正比：$T_{\text{draft}} \propto \gamma$。为了控制延迟，只能使用浅层架构和短候选块，限制了每轮能提出的 token 数。

参考：DSpark 论文 §2 / p4 对 autoregressive drafters 的讨论。
:::

::: concept
title: 并行 draft：快，但块内 token 缺乏依赖
why: 一次 forward 生成整个块，但后面 token 质量会衰减。

并行 drafter（如 DFlash）在一个 forward 内产出全部 $\gamma$ 个 draft token，使 $T_{\text{draft}}$ 几乎与块长无关，因此可以使用更大的块（例如 $\gamma=16$）。但块内每个位置无法条件于同一块中其他已采样的 token，当上下文存在多个合理续写（如 “of course” 与 “no problem”）时，可能产生 “of problem” 这类不连贯组合。论文把这种现象称为块内一致性缺失导致的 **suffix decay**：越靠后的 token 被目标模型接受的概率越低。

参考：DSpark 论文 §2 / p4–p5。
:::

::: compare
left: 自回归 draft（Eagle3 路线）
right: 并行 draft（DFlash 路线）

- 依赖建模 | 全局顺序，依赖链长 | 块内各位置互相独立
- Draft 延迟 | $T_{\text{draft}} \propto \gamma$ | $T_{\text{draft}} \approx \text{const}$，可支持大 $\gamma$
- 尾部质量 | 较好 | 易出现 suffix decay
- 验证压力 | 候选短，验证 token 少 | 候选长，低置信度尾部浪费 batch 容量
- 主要瓶颈 | Draft 本身串行 | 验证开销与接受率衰减
:::

::: qa
question: 既然自回归 draft 建模能力强，为什么不用更深的 draft 模型生成更长的候选？
section_id: m1-drafter-tradeoffs
answer: |
  理论上可以，但工程上 draft 延迟会吃掉加速收益。

  投机解码的总延迟 = draft 生成时间 + 目标模型验证时间。目标模型验证 $\gamma$ 个 token 的延迟基本和验证 1 个 token 相当（memory-bound 小 batch 场景），所以增加 $\gamma$ 几乎是“免费的”。但自回归 draft 每多生成 1 个 token 就要多一次 forward，$T_{\text{draft}} \propto \gamma$。

  一旦 draft 模型加深或 $\gamma$ 加大，draft 时间可能接近甚至超过目标模型验证时间，导致：
  - 总延迟没有下降；
  - 每轮名义上验证了很多 token，但 draft 已经花了太多时间；
  - 端到端 speedup 反而变差。

  因此自回归 drafter 通常被迫采用极浅架构（如 Eagle3 的 1 层）和中等块长，把重心放在“尽量猜准”而不是“尽量猜多”。

  参考：DSpark 论文 §2 / p4："This explicit dependency gives strong modeling capacity, but the drafting cost grows linearly with block size..."
:::

::: qa
question: 并行 draft 的 suffix decay 为什么是“越靠后接受率越低”，而不是随机波动？
section_id: m1-drafter-tradeoffs
answer: |
  因为块内后面的 token 是在“不知道前面具体选了哪个 token”的条件下生成的。

  以论文中的例子为例：假设上下文后面很可能接 “of course” 或 “no problem”。并行 draft 在生成第 2 个 token 时，第 1 个 token 还没有被具体采样出来，所以第 2 个位置只能对第 1 个位置的所有可能取值做边缘化（marginalize）。这会导致它既可能生成 “course” 也可能生成 “problem”，而它们只有分别跟在 “of” 或 “no” 后面才合理。

  具体后果：
  - 第 1 个位置采样出 “of” 后，第 2 个位置如果是 “problem” 就大概率被拒绝；
  - 第 1 个位置采样出 “no” 后，第 2 个位置如果是 “course” 也大概率被拒绝。

  因此**第一个 token 被接受后，第二个 token 的条件接受率已经低于无条件接受率**；同理，第三个 token 要在前两个都正确的情况下才有效，接受率进一步累积下降。这就是 suffix decay 的结构性来源。

  参考：DSpark 论文 §3.1 / p5："a parallel drafter may produce incoherent combinations such as 'of problem' or 'no course'... Acceptance rate thus decays rapidly along the block"。
:::

## [m1-throughput] 端到端加速公式与数值感受

::: concept
title: 投机解码 speedup 公式
why: 把接受率、draft 开销、块长统一到一个可计算的框架里。

假设：
- 目标模型一次验证 $\gamma$ 个 draft token 的延迟约等于 1 个目标步，记为 $T_t$；
- draft 模型生成 $\gamma$ 个 token 的延迟折算成目标步比例为 $\beta = T_d / T_t$；
- 每个 draft token 被独立接受的概率为 $\alpha$。

则一轮投机解码：
- 时间成本 ≈ $T_d + T_t = T_t(1 + \beta)$；
- 期望产出的 token 数 = $1 + \alpha + \alpha^2 + \dots + \alpha^\gamma = \frac{1 - \alpha^{\gamma+1}}{1 - \alpha}$（包含最后从修正分布或 bonus 位置采样的 1 个 token）。

相对于基线自回归（每 $T_t$ 产出 1 个 token）的端到端加速比为：

$$
\text{Speedup} = \frac{1 - \alpha^{\gamma+1}}{(1 - \alpha)(1 + \beta)}
$$

当 $\gamma$ 较大时，$\alpha^{\gamma+1} \to 0$，公式近似为 $\frac{1}{(1 - \alpha)(1 + \beta)}$。这说明：**决定天花板的不是块长，而是接受率 $\alpha$ 和 draft 开销 $\beta$。**

参考：DSpark 论文 §1 / p4 与 §2 对 $T_{\text{draft}}$ 和验证成本的讨论。
:::

::: concept
title: 接受率如何影响端到端 speedup

取固定参数 $\gamma = 5$，$\beta = 0.1$（draft 成本约为目标模型 10%），按上面的公式计算不同接受率下的加速比：

| 单 token 接受率 $\alpha$ | 期望每轮产出 token 数 | 端到端 speedup |
|---|---|---|
| 0.40 | $\frac{1 - 0.4^6}{0.6} \approx 1.66$ | $1.66 / 1.1 \approx 1.51\times$ |
| 0.60 | $\frac{1 - 0.6^6}{0.4} \approx 2.38$ | $2.38 / 1.1 \approx 2.17\times$ |
| 0.75 | $\frac{1 - 0.75^6}{0.25} \approx 3.12$ | $3.12 / 1.1 \approx 2.84\times$ |
| 0.85 | $\frac{1 - 0.85^6}{0.15} \approx 4.15$ | $4.15 / 1.1 \approx 3.77\times$ |
| 0.92 | $\frac{1 - 0.92^6}{0.08} \approx 5.15$ | $5.15 / 1.1 \approx 4.68\times$ |

从表中可以看到：
- 接受率从 0.60 提升到 0.85，speedup 从约 $2.17\times$ 提升到约 $3.77\times$，增幅接近 75%；
- 当 $\alpha$ 接近 1 时，每多提高 0.05 的接受率带来的加速收益会进一步放大。

因此 DSpark 把重点放在“如何让 draft 在长块上仍保持高接受率”，而不是单纯加大 $\gamma$。

参考：DSpark 论文 §1 / p4 指出并行 drafter 的 suffix decay 是限制接受率的关键瓶颈。
:::

::: qa
question: 公式里为什么分子是 $1 - \alpha^{\gamma+1}$，而不是 $1 - \alpha^\gamma$？
section_id: m1-throughput
answer: |
  因为每轮投机解码除了可能接受若干个 draft token，还一定会再产出 1 个 token。

  具体分解：
  - 第 1 个 draft token 被接受的概率是 $\alpha$，贡献期望 $\alpha$ 个 token；
  - 第 2 个 draft token 被接受需要前 1 个也被接受，概率是 $\alpha^2$，贡献期望 $\alpha^2$ 个 token；
  - ……
  - 第 $\gamma$ 个 draft token 被接受的概率是 $\alpha^\gamma$，贡献期望 $\alpha^\gamma$ 个 token。

  把这些加起来：$\alpha + \alpha^2 + \dots + \alpha^\gamma$。

  然后，无论前 $\gamma$ 个 draft token 接受与否，目标模型已经多算了第 $\gamma+1$ 个位置，并且会从该位置采样 1 个 token（bonus token 或修正 token）。所以还要再加 1。

  总期望产出 = $1 + \alpha + \alpha^2 + \dots + \alpha^\gamma = \frac{1 - \alpha^{\gamma+1}}{1 - \alpha}$。

  如果漏掉最后的 +1，就会错误地认为“全部拒绝时本轮产出 0 个 token”，这与投机解码的保底机制矛盾——每轮至少产出 1 个 token。

  参考：Leviathan et al., *Fast Inference from Transformers via Speculative Decoding*，§2.1 对每轮产出的分析。
:::

## [m1-dspark-intro] DSpark 是什么

::: evidence
claim: DSpark 是 DeepSeek-AI 与北京大学研究者提出的投机解码框架，通过半自回归 draft 与置信度调度验证加速 LLM 推理。

status: verified
basis: 论文标题、作者单位（DeepSeek-AI、Peking University）及摘要明确描述 DSpark 为 "Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation"。
:::

::: evidence
claim: 在 DeepSeek 在线服务中，DSpark 让 DeepSeek-V4-Flash 每用户生成速度提升 60–85%，V4-Pro 提升 57–78%。
source: [DSpark 论文 PDF](https://github.com/deepseek-ai/DeepSpec/blob/main/DSpark_paper.pdf)
status: verified
basis: 论文 §5.2 / Figure 7 给出在不同 SLA 下，V4-Flash 在严格延迟约束下 TPS 提升 +85%，V4-Pro 提升 +78%；宽松约束下吞吐分别提升 +51% 和 +52%。
:::

::: compare
left: 标准自回归解码
right: DSpark 投机解码

- 每步产出 | 1 个 token | 平均多个 token（接受长度决定）
- 主要瓶颈 | KV-cache 带宽、串行依赖 | draft 质量与验证效率
- 输出质量 | 与目标模型一致 | 理论上无损（保持目标分布）
- 额外成本 | 无 | 需要训练/加载 draft 模块
:::

::: concept
title: DSpark 的两条核心改进
why: 它同时解决了“draft 不够快/不够准”和“验证不够聪明”两个问题。

1. **半自回归生成（Semi-Autoregressive Generation）**：用并行 backbone 保证 draft 速度，再用轻量 sequential head 在块内引入局部顺序依赖，缓解 suffix decay。
2. **置信度调度验证（Confidence-Scheduled Verification）**：给每个 draft token 估计被接受的概率，根据系统负载动态决定验证多长，把 batch 容量留给高置信度前缀。

这两条改进分别对应论文的 §3.1 和 §3.2，也是本课程 [m2](m2.html) 和 [m3](m3.html) 的核心内容。

参考：DSpark 论文 §3 / p5–p9。
:::

## [m1-exercise] 练习：为什么小模型能加速大模型？

::: exercise
假设小模型生成 5 个 token 的成本只有大模型的 1/10，但大模型一次能验证 5 个 token。如果小模型的 5 个 token 中有 3 个被接受，整体能省多少大模型调用？

--- answer
原来需要 3 次大模型调用才能拿到 3 个 token；现在 1 次验证即可拿到 3 个接受 token，加上小模型成本相当于 0.1 次大模型调用。总成本约 1.1 次，近似省掉 2/3 的大模型调用。
---
:::

## [m1-summary] 本章小结

- LLM 推理慢的根源是自回归串行和 KV-cache 开销。
- 投机解码通过“草稿 + 验证”把串行变成批量，并保持目标分布不变。
- 自回归 draft 建模强但 draft 成本高，并行 draft 速度快但存在 suffix decay，两者各有瓶颈。
- 端到端加速由接受率 $\alpha$ 和 draft 开销 $\beta$ 共同决定，单纯加大块长收益有限。
- DSpark 不是新模型，而是给目标模型加的推理加速层，已在 DeepSeek 生产 API 部署。
- 继续学习前，确认你掌握了 Transformer 解码、概率基础和基本推理命令。
