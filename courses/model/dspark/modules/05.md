## [m5-sla-gains] 为什么严格延迟 SLA 的相对增益更大

::: concept
title: 严格 SLA 下 MTP-1 被迫降低并发
why: 基线无法在低延迟下维持有效 batch，可用容量急剧萎缩。

在生产环境中，SLA 指定了每用户最低生成速度（如 35 tok/s/user 或 50 tok/s/user）。当 SLA 变严格时：
- MTP-1 每步只验证 1 个 token，单用户延迟难以压缩；
- 为了满足严格延迟，系统只能减少并发请求数，否则每个用户分到的算力不够；
- 并发数降低后，GPU 的 batch 容量无法被填满，aggregate throughput 大幅下跌。

DSpark 由于每步能验证并产出多个 token，单用户 TPS 更高。在同样严格的 SLA 下，系统可以维持更高的并发，因此 aggregate throughput 的相对提升非常大（V4-Flash 严格 SLA 下 +661%）。

参考：DSpark 论文 §5.2 / p18–p19。
:::

::: concept
title: 一个简化的 SLA 数值感受

假设某 GPU 在 MTP-1 下：
- 每用户需要至少 50 tok/s 才能满足严格 SLA；
- MTP-1 单用户 TPS 约为 40 tok/s，因此无法在该 GPU 上支持该 SLA，或只能把并发压到极低水平，导致 aggregate throughput 只有 1000 tok/s/gpu。

同一 GPU 在 DSpark 下：
- DSpark 单用户 TPS 提升到约 74 tok/s（+85%）；
- 可以在满足 50 tok/s/user SLA 的同时维持更多并发；
- aggregate throughput 提升到约 7400 tok/s/gpu，相对提升 640% 量级。

这就是严格 SLA 下相对增益被“放大”的原因：分母（基线吞吐）已经因为低并发而变得很小，分子的绝对提升被同样的分母除后显得特别大。

参考：DSpark 论文 §5.2 / p19："At the stricter 50 tok/s/user SLA, MTP-1 again enters a low-concurrency regime, yielding a nominal 406% relative throughput advantage for DSpark"。
:::

## [m5-throughput-interactivity] 吞吐与交互性的权衡

::: concept
title: 服务系统同时优化两个矛盾目标
why: 总吞吐和每用户速度不能同时最大化，DSpark 把可行边界向外推。

生产 serving 系统面临两个竞争目标：
- **Aggregate throughput**：单位 GPU 时间内产出的总 token 数，决定能服务多少并发用户；
- **Interactivity（每用户 TPS）**：单个用户感受到的生成速度，对 Agent、实时对话等场景至关重要。

投机解码天然在这两个目标之间做权衡：用额外的 draft/verify 计算换取单用户速度提升。但如果验证策略不当，高并发下大量无效验证反而会压低总吞吐。

DSpark 的 confidence-scheduled verification 让系统根据当前负载动态选择验证长度：
- 负载轻时，多验证几个候选，充分利用空闲算力提升单用户速度；
- 负载重时，截断低置信度尾部，保护 batch 容量以维持总吞吐。

Figure 7 显示，DSpark 把 MTP-1 的吞吐–交互性 Pareto 边界整体向外推：在宽松 SLA 下提升吞吐，在严格 SLA 下维持有效服务能力。

参考：DSpark 论文 §5.2 / p18，Figure 7。
:::

## [m5-load-adaptive] 负载自适应行为

::: concept
title: 并发增加时调度器自动收缩验证预算
why: 防止高并发下的资源争用拖垮所有请求。

论文 Figure 8 展示了两个关键关系：
- 上半部分：aggregate throughput 随并发请求数变化；
- 下半部分：每个请求平均被分配的目标验证预算随并发请求数变化。

观察到的行为：
- 在低至中等并发（V4-Flash < 200，V4-Pro < 150）时，调度器会把验证预算从 MTP-1 的固定 2 个 token 扩展到约 4–6 个 token，利用空闲算力；
- 当并发继续增加，batch 容量成为瓶颈，调度器自动把平均验证预算压缩回接近 2 个 token；
- 这种动态调整让 DSpark 在不同负载下都能保持比 MTP-1 更高的 aggregate throughput。

参考：DSpark 论文 §5.2 / p19，Figure 8。
:::

::: evidence
claim: 在高并发下，DSpark 的 Hardware-Aware Prefix Scheduler 会自动降低每请求验证预算，以避免 batch 容量争用。
source: [DSpark 论文 PDF](https://github.com/deepseek-ai/DeepSpec/blob/main/DSpark_paper.pdf)
status: verified
basis: 论文 §5.2 / p19 对 Figure 8 的分析："As concurrent load increases, the dynamic scheduler automatically restricts the per-request verification length to prevent resource contention"。
:::

## [m5-cost-benefit] 成本收益估算示例

::: concept
title: 一个简化的部署成本收益计算

假设你运营一个在线 API，当前使用 DeepSeek-V4-Pro 自回归服务，高峰期需要 100 张 GPU 才能满足延迟 P99。引入 DSpark-V4-Pro 后，在同样 SLA 下：

| 指标 | 基线（MTP-1） | DSpark | 变化 |
|---|---|---|---|
| 单用户 TPS | 基准 1× | 约 1.57–1.78× | +57–78% |
| 满足 SLA 所需 GPU | 100 张 | 约 56–64 张 | -36–44% |
| 年租赁成本（假设每张 GPU $2 万/年） | $200 万 | $112–128 万 | 节省 $72–88 万/年 |

估算逻辑：
- 如果 DSpark 把单用户 TPS 提升 57%（保守值），则同样的总流量可以用 $1 / 1.57 \approx 0.637$ 的 GPU 数量服务；
- 如果提升 78%，则只需要 $1 / 1.78 \approx 0.562$ 的 GPU 数量；
- 对应节省 36%–44% 的 GPU。

注意：这是理想化估算，未考虑 draft 模块本身的显存开销、调度延迟、集成成本以及任务类型对接受率的影响。实际节省需要在线 A/B 测试验证。

参考：DSpark 论文 §5.2 / p18–p19 给出的 V4-Pro TPS 提升数据。
:::

## [m5-limitations] 局限与适用场景

::: concept
title: 主要局限
why: 任何加速技术都有适用范围和部署成本。

论文明确指出的局限包括：

1. **固定 draft 开销不可回收**。DSpark 每轮都要用并行 backbone 生成完整的 $\gamma$-token 候选块。对于本身接受率很低的复杂查询（如开放域高难度推理），这部分 upfront draft 计算是浪费的。
2. **训练数据与目标模型强相关**。需要为每个目标模型重新生成响应并准备 target cache，迁移成本不低。
3. **效果与任务类型相关**。代码、数学等结构化任务接受率高；开放聊天接受率相对较低。
4. **硬件与生态依赖**。需要大显存部署 V4-Pro；vLLM/SGLang 集成仍在快速迭代。
5. **调度理想化假设**。Algorithm 1 假设 SPS($B$) 单峰；真实系统的异步流水线需要工程适配。

论文也提到未来方向：在 draft 模型内部引入 difficulty-aware early exiting，让低接受率请求跳过完整块生成。

参考：DSpark 论文 §5.2 / p20 "Limitations"。
:::

::: concept
title: 最适合采用的场景
why: 判断是否值得引入 DSpark 要看 workload 和成本结构。

优先考虑 DSpark 的场景：

- 高并发在线服务，延迟敏感（如实时对话、Agent 工作流）。
- 主要生成代码、数学、结构化文本等接受率高的内容。
- 已经在使用 DeepSeek-V4 系列，想降低推理成本。
- 有资源自己训练 draft 模型以适配私有数据分布。

暂时不优先考虑的场景：

- 低并发、批处理任务。
- 开放域聊天为主，且对延迟不敏感。
- 硬件资源不足以部署 V4-Pro。
- 任务本身接受率极低，draft 开销难以回收。
:::

::: qa
question: 严格 SLA 下的 +661% 吞吐提升是不是意味着 DSpark 比 MTP-1 快 7 倍？
section_id: m5-sla-gains
answer: |
  不完全是。这个数字是**相对吞吐提升**，其大小被 MTP-1 在严格 SLA 下的低并发状态放大了。

  具体解释：
  - 严格 SLA（如 50 tok/s/user）要求每用户速度足够快；
  - MTP-1 单用户 TPS 较低，为了满足 SLA 只能把并发数压得很低，导致 aggregate throughput 变得很小；
  - DSpark 单用户 TPS 高，可以在同样 SLA 下维持更高并发，aggregate throughput 因此大得多；
  - 相对提升 = DSpark 吞吐 / MTP-1 吞吐，分母很小，所以比值很大（+661%）。

  更合理的理解方式：
  - 在**宽松 SLA** 下，两者都能正常并发，DSpark 吞吐提升约 +51%（V4-Flash），这更能反映“同负载下的真实效率提升”；
  - 在**严格 SLA** 下，+661% 表示 DSpark 能维持一个 MTP-1 几乎无法维持的服务水平，而不是说每个 token 都快 7 倍。

  论文自己也说明："we treat this point as an indication that DSpark sustains useful throughput under an interactivity target that the baseline cannot efficiently support"。

  参考：DSpark 论文 §5.2 / p19。
:::

## [m5-summary] 课程总结

- **DSpark 不是新模型**，而是 DeepSeek-V4 的投机解码加速层，已在生产 API 部署。
- **半自回归架构**用并行 backbone 保证速度，用轻量 sequential head 缓解 suffix decay。
- **Confidence-Scheduled Verification**根据 token 置信度和系统负载动态分配验证长度。
- **离线指标**上 accepted length 比 Eagle3 提升 26.7–30.9%，比 DFlash 提升 16.3–18.4%。
- **生产指标**上 V4-Flash TPS 提升 60–85%，V4-Pro TPS 提升 57–78%；严格 SLA 下相对增益被基线的低并发状态放大。
- **负载自适应**：并发低时扩展验证预算，并发高时收缩预算，维持吞吐–交互性边界。
- **局限**包括固定 draft 开销不可回收、训练迁移成本、任务类型依赖和生态集成成熟度。
- 部署成本主要是 target cache 存储和 draft 训练，但官方已提供即插即用 checkpoint。
