# Answer

用户针对的句子是：

> 因此，并行评分 K 个 token 的延迟，和采样 1 个 token 的延迟几乎相同。

这句话是投机解码的硬件前提，但没解释清楚“为什么”。核心是：**decode 阶段小 batch 的 Transformer 推理不是被计算量（FLOPs）卡住的，而是被内存访问和通信卡住的**。

展开说三点：

1. **Linear Layers：小 batch 下 matrix multiply 是 memory-bound**
   矩阵乘法的实际时间 ≈ max(计算时间, 访存时间)。小 batch 时权重矩阵很大，但从 HBM 读权重的时间占了主导；多算几个 token 只是让激活向量变宽一点，权重还是读一遍。所以“算 1 个”和“算 K 个”在访存上差别很小。

2. **Attention：KV cache 已经存在，且不随验证 token 数增加**
   验证 token 时，KV cache 里已经有前面所有 token 的 key/value。新加入的 K 个 token 各自算 query，再和已有的 KV 做 attention；KV 不用重新算、也不用重新从内存读很多新东西。

3. **All-reduces：分布式下通信开销固定**
   模型大到跨 device 时，每层都要做 all-reduce。通信量主要取决于模型分片方式和 tensor 大小，不因为你一次验证 K 个 token 就变成 K 倍。

所以“并行评分 K 个 token”并不是把同一层算 K 遍，而是把 batch 维度从 1 扩到 K，而真正的瓶颈（访存、通信、KV cache 读取）几乎没有线性增长。延迟自然和 1 个 token 差不多。
