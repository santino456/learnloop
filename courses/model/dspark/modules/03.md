## [m3-problem] 盲目验证的浪费

::: concept
title: 并行 draft 带来长候选，但 batch 容量有限
why: 生产环境里不是所有候选 token 都值得用大模型验证。

并行 draft 能一次性提出 7 个甚至更多候选 token，但目标模型一次 forward 能验证的 token 数量受 batch capacity 限制。如果不管置信度全部送进去验证：

- 低置信度的尾部 token 大概率被拒绝，白白占用 batch 容量。
- 高并发时，浪费的容量会拖慢所有请求的响应。

论文把这种现象称为 **indiscriminate verification**，是并行 draft 在高并发 serving 中的主要系统瓶颈。

参考：DSpark 论文 §3.2 / p7。
:::

::: concept
title: 验证开销与系统负载强相关
why: 同样的一个候选 token，在轻载和重载下的“机会成本”完全不同。

论文指出，接受率本身随任务类型变化（代码高、开放聊天低），但更重要的是：**验证一个额外 token 的实际成本取决于当前引擎负载**。轻载时，GPU 本来就有空闲算力，多验证几个 token 惩罚很小；高并发时，每个不必要的验证都会占用本可以服务其他请求的 batch 容量，从而拖累整体吞吐。

因此，理想的验证策略不是固定长度或固定阈值，而是把验证 token 当作需要动态分配的稀缺资源：只把 batch 容量分配给“期望回报为正”的候选前缀。

参考：DSpark 论文 §3.2 / p7："under high-concurrency deployments, every unnecessary verification occupies target model batch capacity that could otherwise serve other active requests"。
:::

## [m3-confidence] 置信度头与前缀生存概率

::: concept
title: Confidence head 估计每个 token 被接受的概率
why: 需要提前判断哪些候选 token 更可能被接受。

DSpark 在 draft 模型上加了一个轻量的 **confidence head**。对每个候选位置 $k$，它输出一个标量置信度 $c_k \in (0, 1)$，表示该 token 被目标模型接受的概率。

架构上，confidence head 是轻量线性投影加 sigmoid：

$$
c_k = \sigma\Bigl(w^\top \bigl[h_k;\; W_1[x_{k-1}]\bigr]\Bigr)
$$

其中 $h_k$ 是并行 backbone 在位置 $k$ 的隐藏状态，$W_1[x_{k-1}]$ 是 Markov head 中前一个 token 的 embedding。把 backbone 特征和 Markov 特征拼接起来，使置信度估计同时利用块级语义和局部顺序信息。

参考：DSpark 论文 §3.2.1 / p7，公式 (7)。
:::

::: concept
title: 训练标签来自总变差距离
why: 置信度的监督信号必须反映真实接受概率，而不是简单的 0/1。

Confidence head 的训练标签 $c_k^*$ 是位置 $k$ 的真实接受率，由 draft 分布 $p_k^d$ 与目标分布 $p_k^t$ 之间的总变差距离决定：

$$
c_k^* = 1 - \frac{1}{2} \bigl\|p_k^d - p_k^t\bigr\|_1
$$

直观理解：
- 如果 draft 分布与目标分布完全一致，$\|p_k^d - p_k^t\|_1 = 0$，则 $c_k^* = 1$，该 token 一定被接受；
- 如果两者完全不重叠，$\|p_k^d - p_k^t\|_1 = 2$，则 $c_k^* = 0$，一定被拒绝；
- 一般情况 $c_k^* \in (0, 1)$，表示按拒绝采样规则被接受的概率。

这个标签可以直接从训练时 target model 和 draft model 的输出分布计算得到，不需要额外人工标注。

参考：DSpark 论文 §3.2.1 / p7，公式 (8)。
:::

::: evidence
claim: Confidence head 输出的是单 token 被接受概率，前缀生存概率通过连乘得到。
source: [DSpark 论文 PDF](https://github.com/deepseek-ai/DeepSpec/blob/main/DSpark_paper.pdf)
status: verified
basis: 论文 §3.2 给出 $c_{r,j}$ 与 $a_{r,j} = \prod_{i \le j} c_{r,i}$ 的定义。
:::

## [m3-survival-calc] 前缀生存概率计算

::: concept
title: 前缀生存概率是条件接受率的累积乘积
why: 投机解码只接受连续前缀，因此第 $j$ 个 token 能产出价值的前提是前 $j$ 个全对。

对请求 $r$ 的候选块，位置 $j$ 的前缀生存概率定义为：

$$
a_{r,j} = \prod_{i \le j} c_{r,i}
$$

它表示“第 1 到第 $j$ 个 token 全部被目标模型接受”的概率。因为 speculative decoding 一旦遇到第一个拒绝位置就停止验证，所以 $a_{r,j}$ 越高，把该前缀送入目标模型验证的期望收益越大。

参考：DSpark 论文 §3.2.2 / p8。
:::

::: concept
title: 前缀生存概率的数值计算

假设某请求生成 5 个候选 token，confidence head 给出各位置的条件接受概率：

| 位置 $j$ | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| $c_{r,j}$ | 0.95 | 0.90 | 0.85 | 0.60 | 0.30 |

逐步计算前缀生存概率 $a_{r,j}$：

- $a_{r,1} = 0.95$
- $a_{r,2} = 0.95 \times 0.90 = 0.855$
- $a_{r,3} = 0.855 \times 0.85 \approx 0.727$
- $a_{r,4} = 0.727 \times 0.60 \approx 0.436$
- $a_{r,5} = 0.436 \times 0.30 \approx 0.131$

如果当前 batch 容量只能再容纳 2 个验证 token，应该优先验证到位置 2（生存概率 0.855），而不是位置 5（0.131）。位置 4 和 5 虽然可能偶尔被接受，但期望收益低，占用容量不划算。

参考：DSpark 论文 §3.2.2 / p8 对 $a_{r,j}$ 的定义与使用方式。
:::

::: qa
question: 为什么前缀生存概率是连乘而不是连加？
section_id: m3-survival-calc
answer: |
  因为“前 $j$ 个 token 全部被接受”是一个联合事件，需要每个 token 都同时满足接受条件。

  在 speculative decoding 中，验证是按顺序进行的：
  - 第 1 个 token 被接受，才继续检查第 2 个；
  - 第 2 个 token 被接受，才继续检查第 3 个；
  - 以此类推。

  如果其中任何一个位置被拒绝，整个验证过程立即停止，后面的 token 不再有机会被接受。

  因此：
  $$
  P(\text{前 } j \text{ 个都被接受}) = P(\text{第 1 个被接受}) \times P(\text{第 2 个被接受} \mid \text{第 1 个被接受}) \times \dots
  $$

  在 confidence head 的设定里，$c_{r,j}$ 已经是“在前面全部接受条件下第 $j$ 个被接受”的概率，所以直接连乘即可：
  $$
  a_{r,j} = \prod_{i \le j} c_{r,i}
  $$

  如果是连加，就会错误地把多个条件概率当成互斥事件处理，得到远大于 1 的“概率”，在数学上是不成立的。

  参考：DSpark 论文 §3.2.2 / p8。
:::

## [m3-scheduler] Hardware-Aware Prefix Scheduler

::: concept
title: 把验证长度选择变成全局吞吐最大化问题
why: 验证长度应该随负载变化，而不是固定值。

DSpark 的调度器把 $R$ 个活跃请求的候选前缀统一考虑。对每个请求 $r$，设其候选长度为 $\gamma$，置信度序列为 $c_{r,1}, \dots, c_{r,\gamma}$，调度长度为 $\ell_r \in \{0, \dots, \gamma\}$。

定义：
- 总 batch token 数：$B = \sum_{r=1}^{R} (1 + \ell_r)$；
- 期望成功接受 token 数：$\tau = \sum_{r=1}^{R} \Bigl(1 + \sum_{j=1}^{\ell_r} a_{r,j}\Bigr)$；
- 系统吞吐：$\Theta = \tau \cdot \text{SPS}(B)$，其中 SPS($B$) 是预先 profile 好的不同 batch size 下每秒能执行的 target verification step 数。

调度器的目标是选择 $\ell_1^*, \dots, \ell_R^*$，使得 $\Theta$ 最大。

参考：DSpark 论文 §3.2.2 / p8。
:::

::: concept
title: Algorithm 1 逐步执行

Algorithm 1 的核心是贪心扩展 + 早停：

**输入**：$R$ 个请求，每个请求有 $\gamma$ 个 confidence 分数，以及预 profile 的 SPS($B$) 曲线。

**步骤 1：计算前缀生存概率**
对每个请求 $r$ 和每个位置 $j$：
$$
a_{r,j} = \prod_{i \le j} c_{r,i}
$$

**步骤 2：构造候选空间并排序**
把所有 $(r, j)$ 对（满足 $a_{r,j} > 0$）按 $a_{r,j}$ 从高到低排序。这相当于一个全局的“验证优先级队列”。

**步骤 3：贪心 admit**
初始化：
- 每个请求 $\ell_r = 0$；
- 当前 batch token 数 $B = R$（每个请求至少验证 1 个位置，即 anchor 后的第 1 个 token）；
- 当前期望接受数 $\tau^* = R$（每个请求保底 1 个 token）；
- 当前最优吞吐 $\Theta_{\text{best}} = R \cdot \text{SPS}(R)$；
- 选中的长度 $\ell_r^* = 0$。

按排序后的顺序逐个尝试 admit $(r, j)$：
- 把 $\ell_r$ 更新为 $j$；
- $B \leftarrow B + 1$；
- $\tau^* \leftarrow \tau^* + a_{r,j}$；
- 计算当前吞吐 $\Theta = \tau^* \cdot \text{SPS}(B)$；
- 如果 $\Theta > \Theta_{\text{best}}$，更新 $\Theta_{\text{best}}$ 和选中的 $\ell_r^*$；
- 否则立即 break。

**步骤 4：返回**
返回 $(\ell_1^*, \dots, \ell_R^*)$，即每个请求应验证的候选前缀长度。

参考：DSpark 论文 §3.2.2 / p8，Algorithm 1。
:::

::: qa
question: Algorithm 1 里 $B$ 的初始值为什么是 $R$ 而不是 0？
section_id: m3-scheduler
answer: |
  因为每个请求至少要验证 1 个 token。

  在 speculative decoding 中，即使 draft 模型一个候选都不生成，目标模型每轮也要至少生成 1 个新 token（自回归基线）。DSpark 每个请求最少也会验证位置 1 的 draft token，所以初始 batch 中就有 $R$ 个验证 token（每个请求 1 个）。

  相应地，期望接受数 $\tau^*$ 的初始值也是 $R$：这 $R$ 个保底验证位置每个都会产出 1 个新 token（接受或修正后采样），所以至少贡献 1 个接受 token。

  之后每 admit 一个额外位置 $(r, j)$，$B$ 增加 1，$\tau^*$ 增加 $a_{r,j}$。这意味着我们愿意为增加 1 个验证 token 付出的代价，是期望多接受 $a_{r,j}$ 个 token。

  参考：DSpark 论文 §3.2.2 / p8，Algorithm 1 第 5 行。
:::

## [m3-static-threshold] 为什么静态阈值在高并发下失效

::: concept
title: 静态阈值忽略了系统负载的变化
why: 同样的置信度阈值，在轻载和重载下的最优决策不同。

早期方法（如 Huang et al., 2024；Li et al., 2024b）通常用一个固定置信度阈值来决定验证长度：超过阈值就验证，低于就截断。这种做法在单请求或低并发场景有效，但在生产环境中会遇到两个问题：

1. **负载轻时过于保守**：阈值设得太低，会错过很多其实值得验证的候选；阈值设得太高，又会在 GPU 空闲时浪费算力。
2. **负载重时不够灵活**：固定阈值无法感知当前 batch 已经有多大。一个候选在 batch 很小时可能值得验证，在 batch 已经很大时可能就不值得。

DSpark 的调度器把“是否验证某个 token”转化为全局优化问题，通过 SPS($B$) 显式建模 batch size 对吞吐的影响，从而在不同负载下做出不同决策。

参考：DSpark 论文 §3.2.2 / p8："Prior methods typically apply a static threshold to confidence scores... static thresholds can be suboptimal in high-concurrency production systems"。
:::

::: concept
title: 同一候选在两种负载下的不同命运

假设 SPS($B$) 曲线如下（单位：step/s）：

| $B$ | 10 | 50 | 100 | 200 |
|---|---|---|---|---|
| SPS($B$) | 120 | 100 | 70 | 35 |

某请求第 3 个候选位置的前缀生存概率 $a_{r,3} = 0.75$。当前 $\tau^* = 50$，考虑是否 admit 这个位置。

**场景 A：轻载，$B = 10$**
- 当前吞吐：$\Theta_{\text{best}} = 50 \times 120 = 6000$
- admit 后：$B = 11$，假设 SPS(11) ≈ 119，$\tau^* = 50.75$
- 新吞吐：$50.75 \times 119 \approx 6039 > 6000$
- **结论**：值得验证。

**场景 B：重载，$B = 200$**
- 当前吞吐：$\Theta_{\text{best}} = 50 \times 35 = 1750$
- admit 后：$B = 201$，假设 SPS(201) ≈ 30，$\tau^* = 50.75$
- 新吞吐：$50.75 \times 30 \approx 1522 < 1750$
- **结论**：不值得验证，应把容量留给更高生存概率的候选。

同一个 $a_{r,3} = 0.75$ 的候选，在轻载下应该进 batch，在重载下应该被截断。静态阈值无法做出这种区分。

参考：DSpark 论文 §3.2.2 / p8 对负载依赖性的讨论。
:::

## [m3-early-stopping] 早停机制与无损保证

::: concept
title: 早停保证非预期性（non-anticipating）
why: 如果调度决策依赖了未来 token，就会破坏投机解码的分布不变性。

Confidence head 的输入包含 $W_1[x_{k-1}]$，即前一个已采样 token 的 Markov embedding。因此，要计算 $a_{r,k+1}$，必须先知道 $x_{r,k}$ 具体是什么。如果调度器在做位置 $k$ 的截断决策时，回头看了 $a_{r,k+1}$，就相当于把未来 token $x_{r,k}$ 的信息泄露进了当前决策，违反了 non-anticipating 性质，会导致目标分布无法精确恢复。

Algorithm 1 通过**早停**避免这个问题：一旦当前吞吐不再提升（$\Theta \le \Theta_{\text{best}}$），就立即停止 admit。此时截断长度只依赖于已经处理过的前缀，不涉及任何未来的 $x_{r,k}$。

参考：DSpark 论文 §3.2.2 / p9 对 lossless guarantee 与早停的分析。
:::

::: qa
question: 早停后得到的一定是全局最优吗？什么情况下会不是？
section_id: m3-early-stopping
answer: |
  论文指出，早停得到全局最优的充分条件是目标函数 $\Theta = \tau \cdot \text{SPS}(B)$ 是单峰的（unimodal）。

  直观上，单峰意味着：随着我们不断 admit 更多候选，吞吐先上升到一个峰值，然后单调下降。这种情况下，早停在峰值处停止，自然就是全局最优。

  但在真实硬件上，SPS($B$) 曲线可能不是光滑的：
  - 某些 batch size 可能因为 GPU kernel launch、通信同步等原因出现“锯齿”或“悬崖”；
  - 真实系统是异步流水线，而不是理想化的同步模型。

  因此，严格来说 Algorithm 1 的早停在非光滑 SPS 曲线下是局部最优的近似。论文在 §5.2 提到，生产部署中会结合异步调度和 Zero-Out-of-Sequence（ZOS）机制做工程适配：用异步性制造因果屏障，允许全局搜索而不泄露未来 token 信息。

  参考：DSpark 论文 §3.2.2 / p9："This stepwise early-stopping yields the global maximum throughput if and only if the objective $\Theta$ is unimodal"；以及 §5.2 的工程适配。
:::

## [m3-training-objective] 训练目标

::: evidence
claim: DSpark 的训练目标由交叉熵、总变差和置信度三项损失加权组成，默认权重 $\alpha_{\text{ce}}=0.1$、$\alpha_{\text{tv}}=0.9$、$\alpha_{\text{conf}}=1.0$。
source: [DSpark 论文 PDF](https://github.com/deepseek-ai/DeepSpec/blob/main/DSpark_paper.pdf)
status: verified
basis: 论文 §3.3 描述损失函数及默认权重。
:::

::: concept
title: 三项损失各司其职
why: 同时优化 draft 质量、与目标分布的对齐度、以及 confidence 估计准确度。

训练总损失为：

$$
\mathcal{L} = \alpha_{\text{ce}} \mathcal{L}_{\text{ce}} + \alpha_{\text{tv}} \mathcal{L}_{\text{tv}} + \alpha_{\text{conf}} \mathcal{L}_{\text{conf}}
$$

| 损失项 | 作用 | 默认权重 |
|--------|------|----------|
| $\mathcal{L}_{\text{ce}}$ | 标准交叉熵，保证 draft 分布合理 | 0.1 |
| $\mathcal{L}_{\text{tv}}$ | 总变差损失，让 draft 分布与目标模型更接近 | 0.9 |
| $\mathcal{L}_{\text{conf}}$ | 置信度头损失，让 confidence 估计更准确 | 1.0 |

总变差损失直接对应 confidence head 的训练标签来源：最小化 $\|p^d - p^t\|_1$ 等价于提升 $c_k^* = 1 - \frac{1}{2}\|p^d - p^t\|_1$。

参考：DSpark 论文 §3.3 / p9，公式 (12)。
:::

## [m3-exercise] 练习：计算前缀生存概率

::: exercise
假设某请求有 5 个候选 token，置信度分别为 0.95、0.90、0.85、0.60、0.30。请计算前 3 个 token 全部 survive 的概率，并判断是否应该验证第 5 个 token。

--- answer
前 3 个 token 全部 survive 的概率 = 0.95 × 0.90 × 0.85 ≈ 0.727。

第 5 个 token 的前缀 survive 概率 = 0.95 × 0.90 × 0.85 × 0.60 × 0.30 ≈ 0.131。在 batch 容量紧张时不值得验证，应优先把容量留给更高置信度的前缀。
---
:::

## [m3-summary] 本章小结

- 并行 draft 的长候选如果全部验证，会浪费宝贵的 batch 容量。
- Confidence head 给每个 token 估计条件接受概率 $c_k$，并用总变差距离 $c_k^* = 1 - \frac{1}{2}\|p_k^d - p_k^t\|_1$ 作为训练标签。
- 前缀生存概率 $a_{r,j} = \prod_{i \le j} c_{r,i}$ 表示前 $j$ 个 token 全部被接受的概率。
- Hardware-Aware Prefix Scheduler 把验证长度选择转化为全局吞吐最大化问题，按 $a_{r,j}$ 排序贪心 admit。
- 静态阈值无法感知系统负载，高并发下会做出次优决策。
- 早停机制保证调度决策只依赖已处理前缀，维护投机解码的 lossless 性质。
- 训练目标同时优化 draft 质量、分布一致性和置信度估计。
