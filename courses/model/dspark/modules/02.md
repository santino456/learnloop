## [m2-paradigms] 两类 draft 范式

::: concept
title: 自回归 draft：Eagle3 路线
why: 顺序生成能建模 token 间依赖，但 draft 本身也有串行成本。

Eagle3 是 2025 年代表性的自回归投机解码方法。它用一个极小的 draft 模型（通常 1 层）依次生成候选 token，并依赖目标模型的特征做条件。优点是：

- 每个 draft token 都显式依赖前面已采样的 token，序列内一致性强。
- 在代码、数学等结构化任务上接受率较高。

缺点是：

- draft 成本随候选长度线性增长。
- 当需要一次性提出长候选序列时，draft 本身会成为瓶颈。

延伸阅读：
- [EAGLE-3: Scaling up Inference Acceleration of Large Language Models via Training-Time Test](https://arxiv.org/abs/2503.01840)
:::

::: concept
title: 并行 draft：DFlash 路线
why: 一次 forward 生成整个 token 块，速度极快，但后面 token 质量会衰减。

DFlash 用块级扩散模型（block diffusion）做并行 draft，把整个候选块一次性生成。优点是：

- draft 时间与块长基本无关，常数时间产出长序列。
- 在短候选上速度优势明显。

但论文指出，并行 draft 存在一个关键问题：**suffix decay**。块内后面的 token 缺乏对前面已生成 token 的显式依赖，导致越靠后的 token 被目标模型接受的概率越低。

延伸阅读：
- [DFlash: Block Diffusion for Flash Speculative Decoding](https://arxiv.org/abs/2602.06036)
:::

## [m2-dflash-backbone] DFlash 并行 backbone 与 KV 注入

::: concept
title: 用目标模型的特征增强 draft 上下文
why: 让 draft 模型在生成候选时直接看到目标模型的内部表示。

DSpark 的并行 backbone 直接复用 DFlash 的结构。在 prefill 阶段，目标模型若干层 $\{l_1, \dots, l_m\}$ 的隐藏状态被抽取出来，拼接后投影到 draft 的隐藏空间：

$$
H_{\text{ctx}} = \text{RMSNorm}\bigl(W_c [H^{(l_1)}; \dots; H^{(l_m)}]\bigr)
$$

其中 $W_c \in \mathbb{R}^{d \times md}$ 是一个共享投影矩阵，$d$ 是 draft 隐藏维度。这些上下文特征随后被注入到 draft 的每一层：

$$
K_i = [W_K^i H_{\text{ctx}};\; W_K^i H_d], \qquad
V_i = [W_V^i H_{\text{ctx}};\; W_V^i H_d]
$$

即把目标模型上下文和目标模型生成的 anchor token 对应的 draft 表示拼接起来作为 key/value。块内所有位置对彼此双向可见，同时也能 attend 到注入的目标上下文。draft 模型复用目标模型的 embedding 层和语言建模头（均冻结），保证 token 空间严格对齐。

参考：DSpark 论文 §3.1 / p4，公式 (2)–(3)。
:::

::: qa
question: 为什么要“注入”目标模型的 hidden state，而不是直接把目标模型最后一层输出给 draft 看？
section_id: m2-dflash-backbone
answer: |
  因为目标模型不同层的特征携带不同粒度的信息，而 draft 模型需要的特征维度与目标模型不同。

  论文选择从多个中间层 $\{l_1, \dots, l_m\}$ 抽取隐藏状态，而不是只用最后一层，原因是：
  - 浅层特征更接近输入 token 的局部语义；
  - 深层特征更接近目标模型的输出分布；
  - 拼接多层相当于给 draft 提供多尺度信号。

  抽取后通过 $W_c$ 投影到 draft 隐藏空间 $d$，是为了让 draft 的 attention 层能直接消费这些特征。如果不投影，目标模型 hidden dim 和 draft hidden dim 不一致，无法直接拼接进 key/value。

  另外，把上下文特征注入到**每一层**而不是只在输入层加一次，可以让 draft 在网络深处持续利用目标信息，而不是只做一个浅层的“提示”。

  参考：DSpark 论文 §3.1 / p4，公式 (2)–(3)。
:::

## [m2-anchor] Anchor Token 机制

::: concept
title: Anchor token 减少 draft 输入长度
why: 用 1 个真实 token 代替前面一长串上下文，既保留条件信息，又降低 draft 计算量。

在标准的投机解码中，draft 模型生成下一个候选块时，需要把前面已生成的所有 token（即完整前缀）作为输入。DSpark 采用 anchor token 机制：每个候选块只以上一轮目标模型验证通过后的**第一个 token**（anchor）作为条件输入，后面跟着 $\gamma - 1$ 个 mask token。

也就是说，输入序列是：

$$
x_0,\; \text{[MASK]}_1,\; \text{[MASK]}_2,\; \dots,\; \text{[MASK]}_{\gamma-1}
$$

其中 $x_0$ 是 anchor token。这样 $\gamma$ 个输入 token（1 个 anchor + $\gamma - 1$ 个 mask）仍然能产出 $\gamma$ 个 draft logits：anchor 本身作为第 1 个预测位置，每个 mask 位置对应块内后续位置。

优势：
- draft 模型不需要重新处理长上下文，输入序列长度恒为 $\gamma$；
- 由于 backbone 已经把目标模型的上下文特征通过 KV 注入带进来了，anchor 足以提供块内采样的局部条件；
- 显著降低 draft 的 attention 和 FFN 计算量。

参考：DSpark 论文 §3.1 / p5–p6 对 anchor token 的描述。
:::

::: concept
title: 没有 anchor 与有 anchor 的输入对比

假设已经生成了前缀 “The cat sat on the ...”，现在要 draft 下 4 个 token。

**无 anchor 机制**：
- draft 输入："The cat sat on the" 的全部 token + 4 个 mask；
- 输入长度 ≈ 上下文长度 + 4；
- 随着对话变长，draft 的 attention 成本线性增长。

**DSpark 的 anchor 机制**：
- 上一轮验证后，最后一个被接受的 token 是 "the"；
- draft 输入："the" + 4 个 mask；
- 输入长度固定为 5；
- 上下文信息通过 KV 注入从目标模型传递过来，不依赖 draft 输入长度。

这样即使序列已经生成上千 token，draft  backbone 的输入长度仍然是固定的 $\gamma$，避免长上下文带来的二次计算开销。

参考：DSpark 论文 §3.1 / p6："uses the anchor itself as the first prediction position, so $\gamma$ input tokens (anchor + $\gamma-1$ masks) yield $\gamma$ draft logits"。
:::

## [m2-sar-arch] DSpark 的半自回归设计

::: concept
title: 并行 backbone 负责“快”
why: 保留并行 draft 的高吞吐优势。

DSpark 首先用一个并行 backbone 在单个 forward 内生成整个候选块。这相当于继承了 DFlash 的高吞吐特性：给定 anchor token $x_0$，一次性产出后续 $\gamma$ 个位置的初始 logits $U_1, \dots, U_\gamma$。

论文把这一步称为 **parallel stage**。anchor token 加上若干 masked 位置进入 backbone，得到块内每个位置的 draft 分布。
:::

::: concept
title: 轻量 sequential head 负责“准”
why: 在块内引入局部顺序依赖，缓解 suffix decay。

DSpark 在并行 backbone 之上增加了一个轻量的 **sequential head**（默认是 Markov head，可选 RNN head）。它定义块内的条件分布：

$$
P(X \mid x_0) = \prod_{k=1}^{\gamma} p_k(x_k \mid x_0, x_{<k})
$$

其中每个位置的概率由 backbone 的 base logit $U_k$ 和 sequential head 提供的转移偏置 $B_k$ 共同决定：

$$
p_k(v \mid x_0, x_{<k}) = \frac{\exp\bigl(U_k(v) + B_k(x_0, x_{<k}, v)\bigr)}{\sum_{u \in \mathcal{V}} \exp\bigl(U_k(u) + B_k(x_0, x_{<k}, u)\bigr)}
$$

这里 $\mathcal{V}$ 是词表。 inference 时按 $p_k$ 从左到右采样。由于 sequential head 必须足够轻量（$T_{\text{sequential}} \ll T_{\text{parallel}}$），整体 draft 延迟仍由并行 backbone 主导。

参考：DSpark 论文 §3.1 / p6，公式 (4)。
:::

## [m2-markov-head] Markov Head 的低秩分解

::: concept
title: 一阶转移偏置与低秩近似
why: 用很小的参数量捕获相邻 token 之间的局部依赖。

最简单的 sequential head 只依赖前一个 token，即一阶 Markov 转移 $B(x_{k-1}, x_k)$。理论上这是一个 $|\mathcal{V}| \times |\mathcal{V}|$ 的矩阵 $B$，对 large vocabulary 来说存储和计算都不可接受。

论文采用低秩分解：

$$
B = W_1 W_2, \qquad W_1 \in \mathbb{R}^{V \times r},\; W_2 \in \mathbb{R}^{r \times V}
$$

给定前一个 token $x_{k-1}$，位置 $k$ 的转移偏置向量为：

$$
B(x_{k-1}, \cdot) = W_1[x_{k-1}] \, W_2 \in \mathbb{R}^{V}
$$

其中 $W_1[x_{k-1}]$ 是 embedding 查找，$W_2$ 是 logit 投影。默认秩 $r = 256$，因此存储和每步计算量都很小，sequential loop 的效率得以保证。

参考：DSpark 论文 §3.1 / p6，公式 (5)。
:::

::: concept
title: “of course / no problem” 的 suffix decay 例子

假设上下文后面很可能接两个常见短语：

| 合理续写 | 第 1 个 token | 第 2 个 token |
|---|---|---|
| A | of | course |
| B | no | problem |

**纯并行 draft（无 sequential head）**：
- 第 1 个位置对 “of” 和 “no” 都有一定概率；
- 第 2 个位置在训练时见过 “course” 和 “problem”，但没看到具体第 1 个位置选了谁；
- 因此可能采样出 “of problem” 或 “no course” 这种不连贯组合。

**加入 Markov sequential head 后**：
- 如果第 1 个位置采样出 “of”，Markov head 给 “course” 一个正偏置，给 “problem” 一个负偏置；
- 如果第 1 个位置采样出 “no”，Markov head 给 “problem” 一个正偏置，给 “course” 一个负偏置。
- 于是块内采样更可能产生 “of course” 或 “no problem”，避免无意义组合。

这正是论文用来说明 suffix decay 来源的经典例子：并行 draft 的每个位置边缘化了同一块内其他位置的选择，而 sequential head 把“前一个 token 具体是什么”重新放回条件中。

参考：DSpark 论文 §3.1 / p5–p6。
:::

::: qa
question: Markov head 只看前一个 token，会不会太弱？为什么不用更强的 N-gram 或 RNN？
section_id: m2-markov-head
answer: |
  这是精度与效率的权衡，而 DSpark 的设计目标是把 sequential stage 做得极轻。

  **为什么一阶 Markov 就够了**
  1. 块内相邻 token 的局部依赖是 suffix decay 的主要来源。一旦把 “前一个 token 具体是什么” 放回条件，就能消除大部分 “of problem” 类错误。
  2. 低秩分解 $B = W_1 W_2$ 把存储和计算压得很小：每次只需要一次 embedding lookup 和一次 $r \times V$ 投影，$r=256$ 时开销远小于并行 backbone 的一小层。
  3. Sequential stage 的总延迟必须满足 $T_{\text{sequential}} \ll T_{\text{parallel}}$，否则半自回归的优势就被抵消。N-gram 或更长上下文会线性增加每步计算和存储。

  **RNN head 的角色**
  论文确实尝试了 RNN head，它在某些设置下接受长度略高，但默认部署和生产环境都使用 Markov head。原因是 Markov head 已经能在“足够轻”的前提下获得大部分收益，RNN 的额外复杂度在当前生产收益不够明显。

  参考：DSpark 论文 §3.1 / p6 对 Markov head 和 RNN head 的讨论，以及 §4.3.2 的实验对比。
:::

## [m2-rnn-head] RNN Head 简介

::: concept
title: 可选的 RNN sequential head
why: 在需要更强块内依赖时，用轻量 RNN 扩展 Markov head 的上下文窗口。

除了默认的 Markov head，论文还提到可以用 RNN 作为 sequential head。RNN head 不再只依赖 $x_{k-1}$，而是维护一个随位置更新的隐状态，从而捕获更长的块内上下文。其计算仍然很轻量，保证 $T_{\text{sequential}} \ll T_{\text{parallel}}$。

离线实验中，RNN-head 变体在某些设置下接受长度略高于 Markov-head，但默认实现和主要生产部署都采用 Markov head，因为低秩 Markov 已经能在极小开销下显著缓解 suffix decay。

参考：DSpark 论文 §3.1 / p6 末尾对 RNN head 的提及，以及 §4.3.2 的实验对比。
:::

::: flow
目标模型生成 anchor token
  -> Parallel backbone 一次性产出 γ 个 draft logits
  -> Sequential head 修正块内依赖
  -> 得到带局部顺序依赖的 draft 块
  -> Hardware-Aware Prefix Scheduler 选择验证前缀
  -> 目标模型并行验证
:::

## [m2-summary] 本章小结

- 自回归 draft 准但慢，并行 draft 快但后面 token 容易变差。
- DSpark 的并行 backbone 继承 DFlash 的 KV 注入机制，用目标模型多层特征增强 draft 上下文。
- Anchor token 机制把 draft 输入长度固定为 $\gamma$，避免长上下文重复计算。
- Sequential head 通过 base logit + 转移偏置 $B_k$ 在块内引入局部顺序依赖，数学形式为公式 (4)。
- Markov head 用低秩分解 $B = W_1 W_2$（公式 5）把 $V \times V$ 转移表压缩到可接受规模。
- RNN head 是可选增强，默认部署使用 Markov head。
- 实测在多个目标模型上 accepted length 显著优于 Eagle3 和 DFlash。
